# Запасное размещение «Кампории» на российском сервере

`scripts/serve-node.mjs` запускает тот же собранный интерфейс и API, что и Cloudflare Worker, но хранит данные в локальном SQLite. Это резерв на случай, если конкурсная ссылка Sites плохо открывается из России. **Доступность конкретного адреса из сетей жюри нужно проверить на практике**; география сервера сама по себе её не гарантирует.

Для VM подходят, например, [Selectel Cloud Server с Node.js в России](https://docs.selectel.ru/en/cloud-servers/applications/node-js/), [Timeweb Cloud Server с выбором региона](https://timeweb.cloud/docs/cloud-servers/manage-servers/create-server) или [Yandex Compute Cloud VM](https://yandex.cloud/en/docs/compute/). Здесь не требуется аккаунт конкретного провайдера или его SDK. Нужны Node.js **24+**, публичный IPv4, домен и HTTPS-прокси. Уточните цену, лимиты и срок работы VM до 28 ноября перед заказом.

## Подготовка

1. На компьютере с исходниками выполните `node scripts/build.mjs` в корне проекта.
2. Перенесите на VM папки `dist/server/`, `drizzle/` и `scripts/serve-node.mjs`. Сохраните ту же структуру, например под `/opt/atlas`. Браузерные файлы уже встроены в `dist/server/index.js`.
3. Создайте отдельного системного пользователя для приложения и доступную ему папку `/var/lib/atlas`. Не размещайте базу в публичном каталоге. У приложения должен быть доступ на запись только к папке базы.
4. D1 в Sites и SQLite на VM — две разные базы. Для текущего переноса подготовлен согласованный экспорт 22 таблиц и 9 вложений с проверкой всех строк, порядка сообщений, непрочитанных и SHA-256 файлов. Старые сессии не переносятся. Перед окончательным переключением обновите экспорт, если в исходной публикации менялись записи. Не используйте QA-базу вместо рабочей копии. Новый пустой сервер без экспорта заполнит отдельные демоданные.

Пример переменных для запуска:

```text
HOST=127.0.0.1
PORT=4173
DATABASE_PATH=/var/lib/atlas/atlas.sqlite
TRUST_PROXY=1
PUBLIC_ORIGIN=https://atlas.example.ru
```

`PUBLIC_ORIGIN` должен совпадать с HTTPS-адресом, который видит посетитель: сервер использует его при проверке запросов. Если `PUBLIC_ORIGIN` не задан, при `TRUST_PROXY=1` адрес строится из `X-Forwarded-Proto` и `X-Forwarded-Host`. Включайте доверие к этим заголовкам только когда Node слушает loopback за вашим прокси. По умолчанию сервер слушает `127.0.0.1`, поэтому его порт не должен быть открыт напрямую в интернет.

Запуск после сборки:

```bash
cd /opt/atlas
HOST=127.0.0.1 PORT=4173 DATABASE_PATH=/var/lib/atlas/atlas.sqlite \
TRUST_PROXY=1 PUBLIC_ORIGIN=https://atlas.example.ru \
node scripts/serve-node.mjs
```

Сервер применяет ещё не выполненные `drizzle/*.sql` **только при старте**, в транзакции. При ошибке миграции он не начинает принимать запросы. Для продакшена запускайте **один процесс** приложения на одном SQLite-файле. Перед заменой версии сделайте согласованную резервную копию базы и каталога вложений; миграции нельзя откатить простой заменой кода.

## Постоянный запуск и HTTPS

Пример `systemd` unit `/etc/systemd/system/atlas.service`; путь к `node` уточните через `command -v node`:

```ini
[Unit]
Description=Kamporia competition prototype
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=atlas
Group=atlas
WorkingDirectory=/opt/atlas
Environment=HOST=127.0.0.1
Environment=PORT=4173
Environment=DATABASE_PATH=/var/lib/atlas/atlas.sqlite
Environment=TRUST_PROXY=1
Environment=PUBLIC_ORIGIN=https://atlas.example.ru
ExecStart=/usr/bin/node /opt/atlas/scripts/serve-node.mjs
Restart=on-failure
RestartSec=3
NoNewPrivileges=true
ProtectSystem=strict
ReadWritePaths=/var/lib/atlas
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

После сохранения unit: `sudo systemctl daemon-reload`, затем `sudo systemctl enable --now atlas` и `sudo journalctl -u atlas -f`. Укажите реальный домен вместо `atlas.example.ru`.

Минимальный `Caddyfile`:

```caddyfile
atlas.example.ru {
    encode zstd gzip
    reverse_proxy 127.0.0.1:4173
}
```

Настройте DNS A-запись на публичный IP VM и откройте входящие TCP 80/443 только для Caddy. [Caddy получает и обновляет HTTPS-сертификат автоматически](https://caddyserver.com/docs/quick-starts/reverse-proxy), если домен указывает на VM и порты доступны. Не ставьте Cloudflare-проксирование перед резервным адресом, если задача резервного адреса — обойти риск блокировки Cloudflare у российских провайдеров.

## Хранение файлов

В Sites используются D1 (`DB`) для структурированных записей и R2 (`BUCKET`) для байтов вложений. На VM тот же Worker получает SQLite-адаптер и локальный файловый адаптер `BUCKET`. По умолчанию каталог вложений равен пути базы с суффиксом `.files`: при `DATABASE_PATH=/var/lib/atlas/atlas.sqlite` это `/var/lib/atlas/atlas.sqlite.files`. Его можно явно переопределить переменной `BUCKET_PATH`; каталог должен быть постоянным и доступным на запись только пользователю приложения. Он содержит и байты файлов, и их HTTP-метаданные. Не размещайте его внутри публичного каталога веб-сервера: чтение выполняется через API с проверкой прав.

Не копируйте только SQLite при переносе существующей установки: без файлового каталога ссылки на прикрепления останутся в базе, но байты будут недоступны. D1/R2 в Sites и SQLite/файлы на VM независимы; автоматического переноса между ними нет.

## Резервная копия SQLite и вложений

Для отдельной диагностической копии базы в работающей системе используйте штатную команду [SQLite `.backup`](https://www.sqlite.org/cli.html), а не копирование одного файла базы во время записи:

```bash
sudo -u atlas mkdir -p /var/lib/atlas/backups
sudo -u atlas sqlite3 /var/lib/atlas/atlas.sqlite ".backup /var/lib/atlas/backups/atlas-$(date +%F-%H%M%S).sqlite"
sudo -u atlas sqlite3 /var/lib/atlas/backups/atlas-YYYY-MM-DD-HHMMSS.sqlite "PRAGMA integrity_check;"
```

Для полного восстанавливаемого снимка остановите приложение, создайте резервную копию SQLite штатной командой и скопируйте **весь** каталог вложений в ту же версию резервной копии, затем снова запустите сервис. Остановка исключает расхождение между D1-совместимыми метаданными и файлами во время публикации или удаления черновика. Храните базу и файлы как одну пару; при восстановлении задайте соответствующие `DATABASE_PATH` и `BUCKET_PATH`. Наличие только SQL-дампа или только файлов не является полной резервной копией.

Замените примерное имя файла во второй команде на созданное. Держите несколько копий вне VM и проверьте восстановление на отдельном экземпляре. Для этого нужна утилита `sqlite3`; сама работа приложения от неё не зависит.

## Проверка перед конкурсной подачей

Проверяйте **конкретный опубликованный URL** без VPN с домашнего и мобильного интернета разных российских провайдеров:

1. Страница, стили и весь `/app.js` загружаются, в консоли браузера нет ошибок сети.
2. Входят оба тестовых студента и сотрудник; у студентов действительно разные профиль, расписание и оценки.
3. Созданная заявка видна после обновления страницы и повторного входа.
4. Прямой запрос к чужой заявке или профилю получает отказ, а действия сотрудника доступны только его роли.
5. Основной сценарий работает на ширине **360 px**; проверьте светлую/тёмную темы и уменьшение анимации.
6. Сохраните личное описание/контакт в подробном профиле; проверьте, что чужая краткая карточка не показывает эти поля, а учебные данные нельзя изменить обычным пользователем.
7. Откройте общий и авторский материал, каталог клубов, стену чужого клуба и чат собственного; кнопки публикации должны соответствовать роли.
8. Прикрепите изображение и документ к вымышленной новости, проверьте превью и скачивание до и после перезапуска сервиса. Другой группе не должно быть доступно вложение групповой новости. Лимиты: 5 МБ на файл, 4 файла и 12 МБ суммарно.
9. Повторите проверку в течение конкурса и перед **28 ноября**. Один успешный `curl -I` не доказывает загрузку JS или работоспособность API.

Участник проверял основной адрес из России с VPN. Доступ без VPN ещё не подтверждён. Проверка запасного адреса требует полного сценария из реальных российских сетей.

## Ограничения варианта

SQLite с одним Node-процессом достаточен для конкурсного прототипа и нескольких тестовых аккаунтов. Для нескольких реплик приложения и большого числа одновременных пользователей потребуется общий сервер БД, например PostgreSQL, и замена D1/SQLite-адаптера. Надёжность VM зависит от оплаченного срока, диска, резервных копий, TLS и мониторинга владельца сервера.

Не включайте SQL-фикстуру очистки старых черновиков на рабочей базе.

## Обновление установки до v8

Перед заменой кода сохраните согласованную копию базы и каталога вложений. При следующем старте применяются миграции 0003–0005: календарные исключения, уведомления/курсоры чтения, архив публикаций и административное управление участниками. После обновления проверьте отмену/перенос одной пары и восстановление, чтение уведомления с повторным входом, поступление сообщения при заполненном черновике, изменение группы и доступ к её чату, архивирование и восстановление публикации с вложением. Не переносите локальную QA-базу на конкурсный адрес.

Прогон новых сценариев: `node scripts/smoke-calendar.mjs`, `node scripts/smoke-activity.mjs`, `node scripts/smoke-management.mjs` с четырьмя паролями из окружения. Запускайте последовательно: тесты временно меняют вымышленные записи и возвращают группы/статусы. Перед демонстрацией архивируйте оставшиеся тестовые публикации, сохраняя возможность восстановления.

## Готовый комплект переноса и закрытый доступ

`Kamporia-vps-release.tar.gz` содержит собранный Worker, SQL-миграции, Node-адаптер и шаблоны конфигурации. Ему не нужны Sites, ChatGPT, Cloudflare, внешние шрифты или CDN в браузере. Требуются Node.js 24+, Linux VPS, домен, Caddy 2.8+ и постоянный диск. Это подготовленный комплект: запуск на российском VPS и проверка из российских сетей ещё не выполнены.

Для небольшой демонстрации выбран Selectel Cloud Shared: 1 vCPU 10%, 1 ГБ RAM, HDD 5 ГБ и прямой публичный IPv4, расчёт в панели — 654,88 ₽/месяц. Ранее рассмотренный VDS за 250 ₽ оказался распродан. Это минимальная конфигурация; скорость и свободное место нужно проверить на реальной VM до подачи. Сервер создан в Санкт-Петербурге; установка приложения продолжается. Домен kamporia.ru зарегистрирован владельцем. Регистрация — 120 ₽ за первый год, продление — 450 ₽/год: https://selectel.ru/services/domains/renewal/ .

1. До открытия доступа создайте отдельного пользователя atlas, каталог `/opt/atlas` для программы и `/var/lib/atlas` для данных. Распакуйте релиз в `/opt/atlas`; каталог данных должен быть доступен на запись пользователю atlas. Уточните путь Node через `command -v node`: он должен соответствовать `ExecStart` в `deploy/atlas.service`.
2. Создайте `/etc/atlas/app.env` по образцу `deploy/app.env.example`, задав настоящий HTTPS-адрес. Установите unit в `/etc/systemd/system/atlas.service`; выполните `systemctl daemon-reload` и `systemctl enable --now atlas`.
3. Скопируйте `deploy/Caddyfile.private.example` в конфигурацию Caddy. Создайте `/etc/atlas/gateway.env` по шаблону: собственный домен, имя владельца и bcrypt-хэш отдельного пароля. Для его создания используйте интерактивный `caddy hash-password`; не передавайте пароль аргументом и не вставляйте открытый пароль в исходники. Шаблон без настоящего хэша не даёт пригодного для входа доступа.
4. Для службы Caddy добавьте override `/etc/systemd/system/caddy.service.d/atlas.conf` с `[Service]` и `EnvironmentFile=/etc/atlas/gateway.env`. Перечитайте systemd и проверьте конфигурацию Caddy в окружении этой службы перед запуском. Файлы `/etc/atlas/*.env` должны читаться только root; в репозиторий их не копируйте.
5. Настройте DNS A-запись прямо на IPv4 сервера, без проксирования через Sites/Cloudflare. Откройте для HTTPS-прокси 80/443; внутренний 4173 оставьте на loopback. Внешний посетитель сначала проходит отдельный вход владельца, затем — внутренний вход «Кампории». Демо-пароли не заменяют этот внешний барьер. Позже доступ жюри настраивается отдельным решением владельца.
6. Перед окончательным переносом экспортируйте актуальную базу и файлы из Sites. Не заменяйте данные копией QA-базы. Новый пустой сервер создаёт отдельную демо-базу; автоматической синхронизации с Sites нет. Перенос должен сохранить согласованность метаданных вложений и их байтов. Сделайте резервную копию и проверьте вход, расписание, заявки, журнал, архив и файлы после переноса.
7. Проверьте с отключённым VPN полный сценарий из домашней и мобильной сетей, затем повторите перед подачей. Проверка localhost или запрос с сервера этого не заменяют.

Caddy HTTPS и отдельный вход описаны в официальной документации: https://caddyserver.com/docs/quick-starts/reverse-proxy и https://caddyserver.com/docs/caddyfile/directives/basic_auth .
